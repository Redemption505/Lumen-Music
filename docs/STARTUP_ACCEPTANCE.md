## 2. 场景与采样

| CSV 场景 | 操作与样本要求 | 解释边界 |
| --- | --- | --- |
| `warm` | 同一机器、构建、资料、网络和测量方法；正常关闭且自有进程退出后，间隔固定约 30 秒，再启动；至少 5 次成功样本，同时保留所有失败尝试 | 是既有系统会话中的重复启动；每次仍应由应用启动服务，不能把已运行服务复用混入 |
| `after-reboot` | Windows“重新启动”后，等待固定约 2 分钟，在打开开发工具/播放器前首次启动；至少 3 次不同系统启动会话 | 是系统重启后的首启，仍受系统预读、防病毒及磁盘缓存影响；关闭程序再打开不能标成此项。不要用启用快速启动的关机再开机代替重启 |
| `first-profile` | 专用测试账户或显式隔离的新资料，独立完成首次安装/首次打开；至少 3 个新测试资料 | 衡量新资料首启，不能代替已有收藏、歌单和队列的恢复验收；统计可合并同环境下不同新资料 |

开发机原生重复启动功能验收已完成；后续补齐系统重启首启、新资料首启及必要计时字段。独立朋友电脑至少完成一次首装与首启，再按可参与程度补齐分布。一次结果只能判断该次行为，不能宣称覆盖上述采样要求。原闪退者须在原电脑重走原步骤，结果独立记录。

每组保存一份环境说明：匿名机器编号、Windows 版本/架构、CPU、内存、系统盘类型、显示缩放、电源模式、是否接电、网络状态、应用/JAR 身份、资料规模（只记录数量）、计时方法及其分辨率。机器编号不使用账户名、主机名或私人路径。保持防病毒和日常系统配置，记录当时后台负载。不关闭安全软件、不清理系统缓存、不自动重启电脑。

## 3. 测量点与通过条件

所有启动时刻使用同一个单调计时器，从执行启动动作的 `t0` 开始。人工计时按实际精度记录，例如 0.1 秒记为 100 ms，不填虚假精确值。

| 字段 | 如何观察 | 判定 |
| --- | --- | --- |
| `window_ms` | 真实主窗口首次可见；若用进程窗口句柄探针，应写明 `method=native-handle-probe` | 窗口句柄出现不等于完成首帧绘制；不同方法分组 |
| `ui_ready_ms` | 主界面显示后立即点“本地音乐”，确认切页/滚动有反馈；等待服务时也应能操作本地页面 | 窗口出现后失去响应、崩溃或只有空壳均不算就绪 |
| `service_ms` | 循环读取本次服务的 `/api/health`，确认 `status=ok` 与预期 provider；核对端口所属进程属于本次应用 | 健康接口只能证明服务可用，不能代替主界面曲库加载成功；随后另验收藏/最近播放显示 |
| `proxy_state` / `proxy_ms` | 侧车 `/health` 返回健康且为本次应用自有进程，填 `ready` 与时刻；实际明确提示回退时填 `fallback`，时间留空 | 回退应单独解释，不能填一个虚构的代理就绪时间；未知填 `not-observed` |
| `exit_ms` | 从正常关闭操作到本次应用及其自有 Python/侧车/桌宠退出 | 不能按进程名杀掉其他程序后声明正常退出 |

若 60 秒仍未完成启动，停止计时并将本次记为 `failed`，保留已观察值；异常退出也记为失败。若操作者未测完、环境被干扰或无法确认进程所有权，记为 `incomplete`。未观察的时间留空，不能填 0。服务等待/失败期间的本地播放可用性，使用允许使用的本地样本另验并记录；此 CSV 不代替完整收听验收。

每次启动检查：不自动发声；等待反馈可理解；点击后界面仍响应；旧收藏、歌单、最近播放和暂停队列正常恢复；退出没有桌宠或自有进程遗留。数据保护沿用 [Windows 指南](WINDOWS_GUIDE.md)和 [D 候选](PHASE4_RELEASE_CANDIDATE.md)，不读取或公开私人内容。

**首轮建立基线，不自动给出耗时达标结论。** 每组报告成功/失败/未完成次数，成功样本的中位数、P90（最近秩）与最大值，少量样本的 P90 接近最大值。失败样本不进入成功耗时分布，但保留在总尝试数中。取得重复测量后再明确窗口、可操作和服务的性能预算。后续相同条件中位数增加超过 20% 且超过 500 ms 作为调查触发线，不单凭它宣布回归；核查负载、缓存、资料和网络，并重复受影响组。该线是拟采用的调查规则，不是已测得的产品性能指标。

## 4. 可执行记录与汇总

使用已经声明的 Python 3.10+；记录器只读取 CSV，输出 JSON，不启动程序、不访问用户资料、不联网。记录文件与报告放在被忽略的 `build/` 下。

```powershell
New-Item -ItemType Directory -Path build/startup -Force | Out-Null
if (-not (Test-Path -LiteralPath build/startup/runs.csv)) {
    Copy-Item -LiteralPath docs/templates/startup-runs.csv -Destination build/startup/runs.csv
}
# 按本节字段填写实际观测。空模板会被拒绝，不是有效结果。
$report = python scripts/startup-report.py --input build/startup/runs.csv
if ($LASTEXITCODE -ne 0) { throw '启动记录无效；保留原报告，不写入本次结果。' }
$report | Set-Content -LiteralPath build/startup/report.json -Encoding utf8
```

报告包含输入 CSV 的 SHA-256。`coverage=complete` 只代表该组成功样本数量足够；`performance_verdict=not-assessed` 明确表示工具没有判定性能预算或正式发行。任何失败/未完成行仍须人工处置。工具不验证输入者是否实际重启、操作过界面或确认了自有进程。

| CSV 字段 | 填写规则 |
| --- | --- |
| `run_id` / `started_at` | 唯一尝试编号；实际开始时间，带时区，例如 ISO 8601 的 `+08:00` 或 `Z` |
| `machine` / `boot_id` | 匿名机器编号；可用 `Get-CimInstance Win32_OperatingSystem` 的 `LastBootUpTime` 记录系统启动会话，同一会话保持同一编号 |
| `build_id` / `jar_sha256` | 设置页和包身份中的完整构建号；`Get-FileHash -Algorithm SHA256` 的主 JAR 哈希 |
| `scenario` / `profile` | 上述三种场景；匿名资料编号，同一资料反复启动保持同一编号，新资料使用不同编号 |
| `network` / `method` | 条件标签，例如 `available`、`disconnected`；计时方法，例如 `operator-stopwatch-100ms`，不同方法不合并 |
| `outcome` | `ok`、`failed`、`incomplete`；成功须已观察窗口/UI/服务、正常退出及自有进程释放 |
| 时间字段 | 正数毫秒，未观察留空；`exit_ms` 从关闭动作单独开始计时 |
| `proxy_state` | `ready`、`fallback`、`failed`、`not-observed`；仅 `ready` 填 `proxy_ms` |
| `owned_processes_stopped` | `yes`、`no`、`unknown`；不明确时不能填成功 |

模板见 [startup-runs.csv](templates/startup-runs.csv)，汇总入口见 [startup-report.py](../scripts/startup-report.py)。同一机器/构建的每个系统启动会话至多一行 `after-reboot`；同一新资料至多一行 `first-profile`。跨机器、构建、网络、方法及不同既有资料的结果分别汇总。

## 5. 执行顺序与异常处理

1. 核对候选身份，确认原资料的恢复措施，关闭播放器并检查测试端口未被其他程序占用。已有服务不能当作本轮启动结果，不终止未知服务。
2. 复用已完成的原生重复启动与资料恢复结果；新增测量只补缺失场景或定位启动波动所需证据。原生鼠标接管按当前会话安排，沿用 [第四阶段 §9](../第四阶段.md)。
3. 操作者自行安排系统重启后首启；先填环境与启动会话，再记录本轮时间。独立朋友使用 [试用说明](FRIEND_TRIAL.md)和 [反馈模板](FRIEND_FEEDBACK.md)。
4. 闪退/卡死先保存构建号、时间和步骤，按 [启动失败说明](WINDOWS_GUIDE.md#启动失败与反馈)取得必要信息；不默认收集整个私人目录或原始日志。
5. 依据最慢测量段决定后续工作：窗口前检查原生启动/JVM/JavaFX 初始化；窗口后 UI 卡顿检查界面线程；服务慢检查托管 Python、资料加载和代理启动。先定位再优化，修改后只重验受影响路径及组。

本轮工具校验入口：`python -m unittest discover -s scripts/tests -p test_startup_report.py -v`。它验证分组、失败保留、不完整记录拒绝和统计计算，全部使用合成输入。真正的冷启动、重复启动、实际资料恢复与朋友试用须另有真实观测记录。

## 6. 工程测量的使用边界

代码小迭代可先运行 [工程启动探针](DEVELOPMENT.md#工程启动与界面响应探针)，核对真实 launcher、自有服务、窗口响应和正常退出。它不占用原生输入，也不修改安装版或个人资料。`-RuntimeHome` 测当前生产 classes；`-AppHome` 测镜像生产 JAR，二者都使用完整开发 JDK 与测试驱动。

探针的窗口和服务时间从测试 Java `main` 入口计算，无法直接填为本方案从启动动作开始的原生 EXE 时间。原始报告包含生产来源、驱动哈希和工程场景标记，组间只在相同 JDK、依赖、数据规模与方法下比较；系统会话、磁盘缓存和后台负载仍会影响结果。工程探针通过可证明该测试链正常，不宣称安装版更新、冷启动达标或原闪退者问题已经解决。
